# 制造业业务扫描与扩展路线

## 当前范围

这个项目已经不只是一个基础 Spring Boot 示例。当前后端已经拆成 `gateway`、`user-service`、`biz-service` 三个模块，业务服务里也已经有了轻量 MES 的核心能力。

目前已经实现的业务范围：

- 用户、角色、权限、菜单、登录、退出、Token 黑名单、登录限流、操作日志。
- 产品基础资料：产品编码、产品名称、单位、创建时间、增删改查接口、分页查询、关键字搜索。
- 生产工单：支持产品明细、状态流转、软删除、创建人操作校验、分页和状态筛选。
- 报工管理：草稿、提交、审核通过、驳回、软删除，并通过 RabbitMQ 异步回写工单明细完成数量。
- 质检管理：合格、不合格、不合格评审、处置、返工复检。
- 设备维修：故障报修、主管派单、维修开始、维修完成、报修人确认关闭。
- 入库管理：创建入库单、验收、上架，上架后增加库存。
- 库存管理：库存查询、盘点计划、实盘录入、差异计算、审核后修正库存。
- 出库管理：创建出库单、库存预检查、拣货、复核、确认出库，确认后扣减库存。
- 微服务部署：通过网关路由，使用 Docker Compose 启动 `gateway`、`user-service`、`biz-service`、MySQL、Redis、RabbitMQ。

## 已有主业务流程

### 生产流程

1. 创建生产工单和工单产品明细。
2. 下发生产工单。
3. 开始生产。
4. 针对工单或工单明细创建报工记录。
5. 提交报工。
6. 审核报工。
7. 报工审核通过后，RabbitMQ 消费者异步更新工单明细完成数量。
8. 完工或取消工单。
9. 工单完成后创建质检单。
10. 质检执行合格/不合格，不合格可进入评审和返工复检。

### 库存流程

1. 创建入库单。
2. 验收入库单。
3. 上架入库单并增加库存。
4. 查询库存。
5. 根据产品创建盘点计划。
6. 录入实盘数量。
7. 提交并审核盘点计划。
8. 审核通过后修正库存数量。
9. 创建出库单并预检查库存。
10. 拣货、复核、确认出库，确认后扣减库存。

### 设备维修流程

1. 操作工提交设备故障报修。
2. 主管派单给维修人员。
3. 维修人员开始维修并提交维修结果。
4. 报修人确认后关闭维修工单。

## 面向传统制造业的缺口

你的目标方向是传统制造业，围绕下单、生产、配送、库存几条主线。当前项目对“生产”和“库存”已经有较好的雏形，但“下单到配送”的完整链路还没有建立。

目前缺失或较弱的业务域：

- 客户管理：客户、联系人、收货地址、结算信息等。
- 销售订单：订单主表、订单明细、交期、订单状态、订单到生产的关联。
- 生产计划：销售订单转生产工单、工单拆分/合并、优先级、排产。
- BOM：成品和原材料/半成品的结构关系、用量、损耗。
- 工艺路线：工序、工位、标准工时、工序顺序、工序派工。
- 采购管理：供应商、采购订单、采购收货、采购退货。
- 原材料库存：当前没有区分原材料、半成品、成品库存。
- 库存流水：当前是直接修改库存数量，没有不可变的出入库流水账。
- 仓库模型：目前只有一个 `location` 字符串，没有仓库、库区、货架、库位层级。
- 配送发货：缺少配送单、承运商、物流单号、物流状态、签收、退货。
- 简单财务字段：单价、订单金额、付款状态、开票状态还没有。
- 报表看板：生产进度、库存预警、延期交付、质检合格率、维修响应时间还没有。
- 权限落地：权限数据已经有，但接口级权限校验还不够统一。
- 服务边界：`biz-service` 里仍有用户/角色的副本对象，`/api/logs` 也存在路由归属不清的问题。

## 推荐扩展顺序

### 第一阶段：打通下单到生产

先做销售订单模块，再考虑配送。

建议新增表：

- `customers`：客户主表。
- `customer_contacts`：客户联系人和收货信息。
- `sales_orders`：销售订单主表。
- `sales_order_items`：销售订单明细。

建议状态流：

- `DRAFT`：草稿。
- `CONFIRMED`：已确认。
- `PLANNED`：已排产。
- `IN_PRODUCTION`：生产中。
- `READY_TO_SHIP`：待发货。
- `SHIPPED`：已发货。
- `COMPLETED`：已完成。
- `CANCELLED`：已取消。

关键集成点：

- 销售订单明细关联产品。
- 已确认的销售订单可以生成一个或多个生产工单。
- 生产工单增加 `source_order_id` 和 `source_order_item_id`。
- 工单完成数量回写到销售订单明细的生产进度。

### 第二阶段：增强生产能力

销售订单稳定后，再补 BOM 和工艺路线。

建议新增表：

- `boms`：BOM 主表。
- `bom_items`：BOM 明细。
- `process_routes`：工艺路线主表。
- `process_steps`：工序明细。
- `work_order_operations`：工单工序快照。

关键集成点：

- 创建工单时复制 BOM 和工艺路线快照。
- 生产开始时可以预留或消耗原材料。
- 报工从“按工单/产品”升级为“按工序/工位”。

### 第三阶段：把库存改成可靠流水账

当前库存直接修改数量，查询简单，但不利于追溯。建议保留 `inventory` 作为当前库存快照，同时新增不可变的库存流水。

建议新增表：

- `warehouses`：仓库。
- `warehouse_locations`：库位。
- `inventory_transactions`：库存流水。
- `inventory_locks`：库存锁定或预占。

建议流水类型：

- `STOCK_IN`：入库。
- `STOCK_OUT`：出库。
- `CHECK_ADJUST`：盘点调整。
- `PRODUCTION_IN`：生产入库。
- `MATERIAL_CONSUME`：生产领料/消耗。
- `RETURN_IN`：退货入库。
- `RETURN_OUT`：退货出库。

关键集成点：

- 每一次库存数量变化都写一条流水。
- `inventory` 表只作为当前余额投影。
- 出库和生产领料需要考虑事务锁或乐观锁，避免并发扣减出错。

### 第四阶段：新增配送发货

配送应该建立在销售订单和出库单已经打通之后。

建议新增表：

- `delivery_orders`：配送单主表。
- `delivery_order_items`：配送单明细。
- `carriers`：承运商。
- `shipment_events`：物流轨迹事件。

建议状态流：

- `DRAFT`：草稿。
- `PICKING`：拣货中。
- `PACKED`：已打包。
- `SHIPPED`：已发货。
- `IN_TRANSIT`：运输中。
- `SIGNED`：已签收。
- `CLOSED`：已关闭。
- `CANCELLED`：已取消。

关键集成点：

- 配送单由销售订单或出库单生成。
- 出库完成后，配送单进入已打包或待发货状态。
- 发货时记录承运商、物流单号、发货时间。
- 签收后关闭配送单，并推动销售订单完成。

### 第五阶段：补采购和供应商侧

当 BOM 和原材料库存建立后，再做采购会更自然。

建议新增表：

- `suppliers`：供应商。
- `purchase_orders`：采购订单。
- `purchase_order_items`：采购订单明细。
- `purchase_receipts`：采购收货。
- `purchase_returns`：采购退货。

关键集成点：

- 低库存预警生成采购需求。
- 采购收货生成入库单。
- 供应商来料质量可以接入质检模块。

## 建议服务边界

当前服务：

- `gateway`
- `user-service`
- `biz-service`

近期建议：

- 继续把 MES 相关功能保留在 `biz-service`，先把业务链路跑通。
- 等模块数量和团队协作复杂度上来后，再拆更细的服务。

未来可拆分为：

- `user-service`：用户、角色、权限、菜单、认证。
- `order-service`：客户、销售订单、配送单。
- `production-service`：产品、BOM、工艺路线、工单、报工、质检。
- `inventory-service`：仓库、库位、库存、入库、出库、库存流水、盘点。
- `equipment-service`：设备、维修工单、保养计划。

## 近期开发任务建议

建议下一批任务：

1. 新增销售订单模块。
2. 给生产工单增加销售订单来源字段。
3. 新增库存流水账，先保证库存变化可追溯。
4. 新增配送模块，并关联销售订单和出库单。
5. 新增仓库和库位主数据，替代单一 `location` 字符串。
6. 清理重复的操作日志路由，以及 `biz-service` 中的用户/角色副本对象。
7. 更新 README 和接口文档，让它们和当前微服务/MES 模块保持一致。

## 上服务器前需要注意的风险

- `user-service` 和 `biz-service` 目前都带有同一套 Flyway 迁移，两个服务可能同时管理同一个数据库结构。
- `biz-service` 里还有用户/角色副本对象，长期最好改成明确的客户端 DTO。
- `/api/logs` 在 `user-service` 和 `biz-service` 中都存在，但网关当前路由到 `user-service`。
- README 仍然偏旧，描述的是早期单模块 RBAC 示例。
- 终端输出里能看到部分中文注释/SQL 注释存在编码显示问题，后续维护前建议统一确认 UTF-8。
- 当前测试偏基础，缺少覆盖完整业务流的集成测试。
